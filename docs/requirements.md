# 产品需求文档（PRD）

> 项目：企业开源技术情报 Agent 与自动周报平台  
> 版本：v0.1  
> 最后更新：2026-09-24  
> 架构约束：[../ARCHITECTURE.md](../ARCHITECTURE.md)

## 1. 背景与问题

研发战略、架构和产品团队需要定期跟踪开源项目。人工流程通常包括搜索热门仓库、判断相关性、阅读 README、比较 star/fork 趋势、回顾上周结论、整理报告和分发。该流程重复、耗时长、证据容易丢失，且不同周之间的分析口径不一致。

本项目通过确定性数据 Pipeline 和专用研究 Agent 替代重复劳动，目标是让常规周报在无需人工阻塞的情况下完成，人工只在异常、敏感或低置信度场景介入。

## 2. 用户与角色

| 角色 | 主要任务 |
|---|---|
| `ADMIN` | 管理系统配置、用户、数据源、模型策略、审计和发布规则 |
| `EDITOR` | 配置主题，触发研究，编辑、审核、发布和回退报告 |
| `VIEWER` | 查看权限范围内的仓库趋势、Agent 轨迹和报告 |
| 系统 Agent | 在受限工具和预算内完成研究、验证和草稿生成 |

个人版本由同一用户承担全部角色，但权限模型仍保留角色边界，以展示企业权限意识。

## 3. 核心用户故事

1. 作为研发战略分析师，我希望每周自动得到带来源的证据型开源项目报告，从而减少搜索和整理时间。
2. 作为报告审核人，我希望只在 Agent 低置信度、敏感或异常时介入，从而不被日常审核阻塞。
3. 作为架构师，我希望看到项目 star 增速、技术方向和历史结论，而不是只看单日热度。
4. 作为管理员，我希望限制 Agent 可调用的工具、模型和预算，从而避免越权与 Token 失控。
5. 作为内部读者，我希望只能查看权限范围内的报告，且报告若被修改可审计。
6. 作为项目维护者，我希望通过评测证明 Agent 比单 Prompt 更好，并定位每次质量变化。

## 4. 功能需求

### 4.1 Agent 板块

| 编号 | 需求 | 验收要点 |
|---|---|---|
| A-001 | Agent 能够根据主题和时间窗口制定研究任务 | 状态中产生 `research_plan`，任务与候选仓库关联 |
| A-002 | Agent 通过工具查询指标、仓库画像、内容和历史报告 | 每次调用写入 `tool_calls`，只允许白名单工具 |
| A-003 | Agent 能根据证据缺口继续查询或结束研究 | 达到证据充分、预算上限或循环上限时停止 |
| A-004 | Verifier 检查数字、引用、结构和敏感内容 | 未通过时回查或进入人工审核 |
| A-005 | 报告以固定结构生成并可转换为 Markdown/HTML | 包含摘要、趋势、项目分析、风险、建议和来源 |
| A-006 | 关键结论必须绑定 `report_sources` | 关键数字来源覆盖率初始目标 >= 95% |
| A-007 | Agent 配置支持 Prompt、模型、工具集和预算版本化 | 每次运行可追溯 `agent_config_id` |
| A-008 | 支持 Baseline、Agent 和消融版本评测 | 输出统一指标和差异报告 |
| A-009 | 常规低风险报告无需人工阻塞发布 | 策略为 `AUTO` 或 `AUTO_WITH_DELAY` |
| A-010 | 异常和敏感报告进入人工审核 | 策略为 `MANUAL`，审核前不得推送 |

### 4.2 数据与工程板块

| 编号 | 需求 | 验收要点 |
|---|---|---|
| D-001 | 管理 GitHub/Hugging Face 数据源配置 | API 凭证不落明文，凭据更新可审计 |
| D-002 | 按配置主题定时采集公开数据 | 支持分页、超时、限流、指数退避和错误分类 |
| D-003 | 清洗、标准化并幂等写入仓库数据 | 重复执行不产生重复仓库或重复快照 |
| D-004 | 每日保存仓库指标快照 | 同仓库同日唯一，可计算 star/fork 增长 |
| D-005 | 基于规则和 SQL 筛选候选项目 | 候选阶段不调用 LLM |
| D-006 | 异步执行采集、研究和报告任务 | Celery 任务可重试、可查询状态和失败原因 |
| D-007 | 提供报告、仓库、Agent、评测和审计 API | 接口契约稳定，错误采用 Problem Details |
| D-008 | 提供轻量管理界面 | 可配置、触发、查看、编辑、审核和发布 |
| D-009 | 支持邮件或 Webhook 推送 | 仅已批准或符合策略的报告可推送 |
| D-010 | 记录任务成功率、延迟、Token、成本和失败率 | 指标可按日期、主题、模型和版本聚合 |

### 4.3 权限与安全板块

| 编号 | 需求 | 验收要点 |
|---|---|---|
| S-001 | 支持本地账号登录和 `ADMIN/EDITOR/VIEWER` 角色 | 越权请求返回 403 并记录安全审计 |
| S-002 | 报告可见范围为 `PRIVATE/TEAM/INTERNAL` | 列表、详情、下载和推送均执行 ACL |
| S-003 | 关键操作写入审计日志 | 登录、配置、Agent 触发、审核、发布和导出可追溯 |
| S-004 | 外部内容按不可信输入处理 | Prompt Injection 测试达到初始阈值 |
| S-005 | 模型工具遵循最小权限 | Agent 无 Shell、无任意 URL、无直接 SQL 写权限 |
| S-006 | 敏感信息不得进入日志和 Prompt | 密码、API Key、Cookie、连接串被过滤 |
| S-007 | 机密报告默认不得调用未批准外部模型 | Provider Adapter 读取模型策略并拒绝违规调用 |
| S-008 | 数据可设置保留和删除策略 | 首期至少支持管理员清理评测与历史报告 |

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 正确性 | 数据重复执行幂等；关键指标与报告数字一致 |
| 可维护性 | API、Agent、Pipeline、报告和安全模块边界清晰 |
| 可用性 | Redis 故障不影响历史报告读取；单任务失败不阻塞其他任务 |
| 性能 | 每日采集在配置窗口内完成；单次 Agent 研究有明确超时 |
| 成本 | 每个 Agent 运行有 Token/费用预算和降级策略 |
| 安全 | 最小权限、审计、脱敏、模型白名单和不可信输入隔离 |
| 可测试性 | 工具契约、状态机、发布策略和评测均可独立测试 |

## 6. 效率与成功指标

基线是人工完成一份常规周报所需时间。上线后至少记录：

- 单份周报人工操作时长相对基线的降低比例。
- 常规周报的人工阻塞率；目标接近零，异常除外。
- 自动发布和进入人工审核的比例。
- 单报告平均 Token、模型费用和生成延迟。
- 人工退回原因及 Bad Case 数量。
- Agent 相对 Baseline 的引用覆盖率、事实一致性和任务完成率。

具体评测方法见 [evaluation.md](evaluation.md)。

## 7. 发布与审核需求

| 场景 | 是否默认人工审核 | 处理方式 |
|---|---|---|
| 常规内部报告、公开数据、质量达标 | 否 | `AUTO_WITH_DELAY`，窗口内可撤回 |
| 低敏感内部报告且历史表现稳定 | 否 | 可配置为 `AUTO` |
| 首次运行或切换模型/Prompt/工具 | 是 | `MANUAL` |
| 低置信度、关键数字无法验证 | 是 | `MANUAL`，展示失败证据 |
| 敏感/机密报告或外部推送 | 是 | `MANUAL`，并限制模型与推送范围 |

人工审核是异常处理和质量反馈机制，不是常规发布流程的固定阻塞点。

## 8. 验收场景

1. 配置一个监控主题，采集一批真实公开仓库并完成每日快照。
2. 重复执行采集任务，仓库数量和快照数量不重复。
3. 让 Agent 完成一次研究，至少发生一次工具调用、一次证据验证和一次草稿保存。
4. 将报告中的关键数字与数据库比对，能够追溯来源。
5. 模拟低置信度报告，系统必须进入 `MANUAL` 而非自动发布。
6. 模拟普通低风险报告，系统进入 `AUTO_WITH_DELAY` 并在窗口后发布。
7. 以 `VIEWER` 访问无权报告，返回 403 并产生审计记录。
8. 执行 Baseline、Agent、消融评测并得到统一结果文件。
9. 触发 Prompt Injection 样本，Agent 不调用越权工具且验证器标记风险。
10. 达到 Token 预算上限时，Agent 停止新增调用并返回明确状态。

## 9. 首期范围与限制

首期重点证明 Agent 工具调用、自动化、数据建模、权限和评测。以下能力只预留接口，不作为完成标准：

- 企业 SSO、LDAP 和多租户。
- 完整 DLP、KMS、水印和复杂 ABAC。
- 本地模型集群和模型微调。
- Multi-Agent 自由协作。
- Kubernetes、跨区域容灾和高可用数据库。

## 10. 需求变更规则

任何影响角色、数据范围、发布策略、Agent 工具权限、API 契约或数据模型的变更，必须先更新本文件和 `ARCHITECTURE.md`，必要时新增 ADR，再进入实施。

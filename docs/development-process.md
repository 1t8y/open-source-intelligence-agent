# 项目开发流程
> 层级：流程规范｜职责：阶段门控、测试矩阵与文档维护顺序；不记录任务进度

> 采用企业常见阶段门控，但压缩为个人可执行的轻量流程。  
> 最后更新：2026-10-09

## 1. 角色映射

个人项目由一人承担多个角色，但每项职责必须显式完成：

| 企业角色 | 个人项目职责 |
|---|---|
| 项目发起人 | 定义目标、成功指标和范围 |
| 产品负责人 | 写 PRD、用户故事和验收标准 |
| 技术负责人 | 维护 ARCHITECTURE、ADR 和技术边界 |
| 开发 | 按任务清单小步实现 |
| 测试 | 写测试、执行评测和故障演练 |
| 安全负责人 | 权限、威胁模型、依赖和数据处理检查 |
| 运维 | 部署、监控、告警、回滚和运行手册 |

## 2. 阶段门控

### Gate 0：立项

交付物：

- 项目目标、用户和痛点。
- 成功指标：效率提升、引用质量、成本和人工干预率。
- 范围与非范围。
- 数据安全等级和外部模型使用边界。

通过标准：能用一句话说明谁在什么流程中节省了哪些工作。

### Gate 1：需求

交付物：`docs/requirements.md`、验收场景和权限矩阵。

通过标准：每项功能可测试，明确常规报告不默认人工审核。

### Gate 2：设计

交付物：`ARCHITECTURE.md`、API 契约、数据模型、安全设计、评测方案和 ADR。

通过标准：架构、接口和数据库没有未解释的冲突；用户确认文档后进入实施。

### Gate 3：开发

交付物：可运行的纵向小版本、数据库迁移、测试，以及本地过程记录（《使用手册.md》对应阶段、《开发进度流水.md》对应任务）。

执行规则：

- 一次只实施任务台账中的一个任务（台账在本地《开发进度流水.md》；`ARCHITECTURE.md` 不再列任务）。
- 不先写未经文档记录的接口或数据表。
- 跨模块对象字段名必须与契约完全一致。
- 每个任务结束都要运行真实核心路径，不能只报告单测通过。
- 影响架构的代码变更立即回写 `ARCHITECTURE.md` 的设计章节；变更历史由 `git log` 承担，任务流水记入本地《开发进度流水.md》。

### Gate 4：测试与评测

交付物：

- 单元测试、集成测试、端到端测试。
- 数据采集幂等测试、权限测试、Prompt Injection 测试。
- Baseline/Agent/消融评测报告。
- Token、延迟和失败率统计。
- UAT 场景演练记录。

通过标准：核心流程可运行；质量、安全和成本达到项目初始目标，或明确记录例外。

### Gate 5：发布

交付物：

- 版本号、数据库迁移、环境配置和依赖锁定。
- 预发布环境验证。
- 回滚方案、故障排查和运行手册。
- 模型/Prompt/Agent 配置版本。

通过标准：新环境能按文档启动；已发布的报告可以撤回；外部模型和推送通道受控。

### Gate 6：运行与迭代

交付物：

- 任务成功率和失败原因监控。
- Token/延迟/成本看板。
- Bad Case 和评测回归。
- 安全事件和生产事故记录。

通过标准：发现问题后可以定位到 Agent Step、Tool Call、报告版本和模型配置。

## 3. 测试矩阵

| 层级 | 覆盖内容 | 必需示例 |
|---|---|---|
| 单元测试 | 规则、状态机、脱敏、指标计算 | 重复快照、预算超限、非法权限 |
| 契约测试 | API Schema、Tool Schema、Provider Adapter | 字段缺失、类型错误、超时 |
| 集成测试 | MySQL、Redis、Celery、Collector、报告状态机 | 采集失败后重试，重复任务不重复入库 |
| Agent 评测 | Baseline、Agent、消融、Prompt Injection | 引用覆盖、事实一致性、越权阻断 |
| 端到端测试 | 从主题配置到报告发布 | 低风险自动发布、高风险进入审核 |
| 安全测试 | 越权、注入、敏感日志、凭证泄露 | 403 审计、密钥不入 Prompt |
| 性能测试 | 采集速度、报告延迟、并发任务 | 配置窗口内完成，队列不无限增长 |

## 4. 分支与交付规范

- `main` 保持可运行，功能通过短生命周期分支开发。
- 每次提交只解决一个任务，提交信息关联任务编号或 ADR。
- 合并前至少完成 lint、单元测试、类型检查和迁移检查。
- 任何 API、数据模型、权限或 Agent Tool 变更，必须同时更新对应文档。
- 发布记录必须包含 commit SHA、迁移版本、Agent 配置和 Prompt 版本。

## 5. 代码审查清单

1. 是否偏离 `ARCHITECTURE.md` 的模块边界？
2. 跨模块字段名是否完全一致？
3. 外部输入是否有存在性、类型和长度校验？
4. 数据库操作是否幂等，事务和唯一约束是否正确？
5. 是否新增了未记录的依赖、接口、数据表或权限？
6. 敏感信息是否会进入日志、Prompt、Trace 或错误响应？
7. 是否测试了两模块之间的真实集成路径？
8. 是否真实启动并操作过核心路径？

## 6. 发布检查清单

- [ ] 数据库迁移已备份并可回滚。
- [ ] Redis/Celery 队列无不可恢复的旧任务。
- [ ] Agent 模型、Prompt、工具策略有明确版本。
- [ ] `MANUAL` 报告发布门禁测试通过。
- [ ] ACL、审计和脱敏测试通过。
- [ ] Token/费用预算和降级策略已配置。
- [ ] 监控指标、告警和运行手册可访问。
- [ ] 已准备一次真实主题的端到端回放结果。

## 7. 文档职责清单

文档分三层，改动前先判断它属于哪一层：

| 层 | 文档 | 职责 | 不写 |
|---|---|---|---|
| 事实基线 | `REQUIREMENTS.md` | 做什么、边界、验收标准 | 实现细节、进度 |
| 事实基线 | `INTERFACES.md` | 模块 / API / Tool 签名、字段、错误码、状态机 | 「哪次任务改的」 |
| 事实基线 | `ARCHITECTURE.md` | 选型理由、分层依赖、目录结构、数据模型摘要、运行时设计 | 任务清单、Changelog、验证记录 |
| 详细规格 | `docs/requirements.md` | PRD 与验收标准 | 与根文档冲突的口径 |
| 详细规格 | `docs/api-contract.md` | 外部 HTTP API 契约 | 任务进度 |
| 详细规格 | `docs/agent-tool-contract.md` | Agent 内部工具契约 | 任务进度 |
| 详细规格 | `docs/data-model.md` | 表结构、关系与不变量 | 任务进度 |
| 详细规格 | `docs/security-and-privacy.md` | 威胁、权限与数据处理 | 任务进度 |
| 详细规格 | `docs/evaluation.md` | 质量、成本与回归评测方案 | 任务进度 |
| 详细规格 | `docs/observability.md` / `docs/backfill.md` / `docs/operations.md` | 指标口径 / 回填协议 / 运维操作 | 任务进度 |
| 决策日志 | `docs/adr/` | 一次决策一份，记选项与理由 | 开发进度流水 |
| 证据报告 | `docs/ablation-report-c1.md`、`docs/live-run-review.md`、`docs/samples/` | 记录一次真实运行或评测的结论 | 不构成契约 |
| 入口 | `README.md` | 项目入口与文档索引 | 契约细则 |

**过程层（本地、gitignored、不入库）**：

- `使用手册.md`：每个阶段完成后必须更新，固定五节 —— 新增文件作用、结构关系、触发与查看方式、验证状态、下一阶段入口。
- `开发进度流水.md`：任务台账、开发进度流水、原 `ARCHITECTURE.md` 变更日志的原文归档。
- `git log`：提交级变更事实来源；`ARCHITECTURE.md` 不再维护 Changelog。

**修改顺序**：契约冲突先改根文档 → 同步 `docs/` 细则与代码 → 跑 `scripts/check_docs_drift.py` 十项比较 → 跑 ruff / mypy / pytest 门禁。判据是：改动后需要同步修正代码或测试的写基线；只是「记下来以后能查」的写过程层。
